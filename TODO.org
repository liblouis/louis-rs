    (~Pipeline~) has no way to specify a display table

- [ ] The boundary functions (~word_start~, etc) only work in forward
  translation — confirmed ~uppercase.rs~ has no backward-direction
  logic at all; likely the same root cause behind the backward-caps
  gaps under "Known gaps" below
- [ ] Normalize input text to a canonical Unicode form
  - NFC normalization was tried (input at the start of the pipeline,
    plus rule patterns) but reverted: it fixed tables that define
    rules for precomposed characters (e.g. pt-pt-g1.utb), but broke
    tables that define rules for standalone combining characters (IPA,
    Hebrew, Yiddish) with no table-side workaround available. No
    normalization happens today. NFD normalization is a promising
    alternative — it decomposes all input, so combining marks stay
    explicit and precomposed rules still match via longer trie paths.
  - See ADR in [[file:doc/Architecture_Decision_Records.org][Architecture Decision Records]]

* Known gaps
- [ ] Literal hyphen character breaks per-segment contraction in compounds
  - e.g. en-ueb.yaml: "do-it-yourself" -> expected "d-x-yrf", actual
    "do-x-y|rself" ("do" and "yourself" fail to contract on their own
    side of the hyphen); same for "out-and-out"
  - cause: ~Rule::Hyphen~ (~src/translator/table.rs~) files the hyphen
    under generic ~CharacterClass::Punctuation~ instead of whatever
    classification word-boundary detection needs to treat each side as
    its own word. Unrelated to ~src/hyphenation.rs~/dictionary-based
    hyphenation.
- [ ] ~nocross~ only checks whether the matched candidate substring can
  hyphenate anywhere, not whether a break falls inside *that*
  candidate's span within the enclosing word (liblouis's real,
  positional check, ~syllableBreak()~). Fixing this needs a
  position-aware ~HyphenationTable~ query plus correct
  enclosing-word-bounds computation in ~nocross_candidates()~
  (~src/translator/table/primary.rs~).
- [-] indication + backtranslation
  - [ ] begcaps/endcaps/begcapsphrase/endcapsphrase (passage-level caps)
    — no backward-direction logic at all in ~uppercase.rs~
  - [ ] emphasis (begemph/endemph etc.) — needs a way to return
    typeform metadata from backward translation, not just text
- [ ] Isolated single-letter capitalization (capsletter vs.
  begcapsword tier) — see the ADR of the same name for the full
  analysis. liblouis's begin/end/word/symbol emphasis model allows two
  indicator emissions at one position; our flat per-position
  ~Indicators::precompute()~ model doesn't. Properly fixing this likely
  means unifying ~uppercase.rs~ and ~emphasis.rs~ into one shared tier
  model first.
- [-] inpos + outpos mapping
  - [X] An inserted indicator's (or ~correct~-insertion's) output cell is
    attributed to the character it precedes, as liblouis does
    (~compute_output_positions~, ~src/translator/positions.rs~)
  - [X] A character the translation consumes without producing anything
    now gets the neighbour liblouis gives it, which differs by
    direction: forward the *preceding* cell ("append to previous"),
    backward the character that *follows* ("prepend to next"). liblouis
    keeps one mapping between the braille and the text and only fills
    its gaps on the text side, which is the pipeline's input forward but
    its output backward, so the two position algorithms swap roles
    (~src/translator/positions.rs~).
  - [ ] One ~cursorPos~ mismatch in ~fr-bfu-g2_harness.yaml~, off by one
    on a math-expression/number-sign case — the last position mismatch
    left in the suite
  - [ ] liblouis' undocumented ~-1~ "no output position" value is
    normalized to 0 when reading YAML (~pos_value~, ~src/yaml.rs~).
    That's a guess at intent, pending [[https://github.com/liblouis/liblouis/issues/2080][liblouis#2080]]: if upstream makes
    the sentinel unreachable the normalization becomes dead code, if
    they document it as contract we may instead have to match ~-1~
    semantics for the total-deletion case.
- [-] ~Attribute::Boundary~/~ByOrder~/~Any~ (the attributes inside a
  rule's ~%[...]~/~$...~ set) are mostly no-ops
  - ~Attribute::Boundary~ in match_pattern.rs is now enforced (fixed
    the word/group-sign gap below)
  - [ ] ~ByOrder~/~Any~ in match_pattern.rs, and all three in
    context_pattern.rs, remain no-ops
- [-] Word/group-sign ("lower"/part-word sign) contraction — mostly
  fixed: root cause was ~match~ rules gated on the ~^~ boundary
  attribute never firing, now fixed for both lowercase and capitalized
  input. Remaining gap: double-letter contractions
  (~match %a bb %a 23~) fail for standalone words due to a
  ~BoundaryMode::AssumeAtStart~ bug whose direct fix regresses the
  suite by exposing a bigger architectural gap — see the ADR "Match-rule
  candidate selection: weight vs. table-definition order".
- [ ] Backward translation of those same word/group signs sometimes
  corrupts unrelated surrounding text instead of just failing to
  contract, e.g. sw-ke-dictionary.yaml backward lookups splicing in
  unrelated dictionary words ("wote" -> "wizaraote"), or a "be"
  wordsign backward-translating to "bb"
- [ ] Single-letter words get a spurious letter-sign prefix inserted
  (e.g. "a" -> ⠰⠁, "u" -> ⠰⠥) — seen across unrelated tables
  (en-us-g2, sw-ke), likely one shared root cause
- [ ] Missing leading indicator when it would apply at the very start
  of the input string (seen in en-ueb-computer-code.yaml: ".count" is
  missing its leading ";" marker that mid-string occurrences get)
- [ ] Numeric-mode/capital-sign interaction: letters used as
  pseudo-digits (e.g. Rwandan-style date/verse references in
  rw-rw-g1.yaml) incorrectly receive a capital sign even though
  they're inside number context
- [ ] ~endmodeword~/~endmode~ (~src/translator/indication/mode.rs~) never
  fire when a mode run is immediately followed by a character that is
  the ~base~ of one of the mode's own characters (e.g. ~"1a"~ under
  ~base digit 1 a~, per liblouis's ~tests/yaml/numericmode.yaml~) —
  liblouis's ~resetsEmphMode~ treats such a character as not resetting
  the mode via its ~base~/linked-character chain, which
  ~CharacterClasses~ doesn't currently expose to indication modules.
  Same underlying class of bug as the numeric-mode/capital-sign
  interaction above, just for the generic mode family instead of
  numsign/capsletter. See the module doc in ~mode.rs~ for the full
  analysis.
- [ ] ~digit~'s own ~numericmodechars~/~midendnumericmodechars~
  transparency isn't wired into ~mode_indicator~ (~src/translator/indication/mode.rs~)
  — only ~numeric_indicator~'s numsign/nonumsign use them. Only matters
  for a table combining ~begmode~/~begmodephrase~ (which have a visible
  close) with ~digit~ and a ~-~/~.~-joined run; ~begmodeword~'s close is
  invisible either way so it's unaffected. No table exercises this today.
- [ ] ~emit_group~'s passage-grouping (~src/translator/indication/mode.rs~)
  bridges across a non-boundary gap for a self-bounded class like
  ~digit~, e.g. ~"123a456"~ under ~begmode digit~: a plain letter isn't
  ~is_letter~ when ~letter_chars == active_chars~, so it's treated like
  the "hyphen doesn't split a word" case uppercase.rs deliberately
  allows — but for ~digit~ there's no letter/hyphen distinction, so a
  genuine mode-resetting character gets silently bridged instead of
  closing the run. No table exercises ~begmode~/~begmodephrase~ with
  ~digit~ today.
- [ ] Malayalam conjunct/reph rule: a specific virama/conjunct
  sequence consistently produces ⠗ instead of the expected ⠻
  (ml.yaml)
- [ ] ~compbrlAtCursor~/~compbrlLeftCursor~ translation modes not
  implemented — mode flags in ~TranslationOptions~ meant to expand the
  current word into computer braille without ~begcomp~/~endcomp~
  indicators
- [ ] The YAML suite is not deterministic: repeated ~check~ runs of the
  same binary report different results for ~fr-bfu-g2.yaml~ (94.5–95.0%)
  and ~pa.yaml~ (87.1–87.3%). Not caused by the position work — plain
  ~main~ varies the same way. Worth chasing before trusting the suite to
  catch small regressions, since a few tests flipping is exactly the
  size of a real regression. Both files have several ~table:~ blocks and
  the runner is parallel (~rayon~), so shared state or iteration order
  in table compilation is the first place to look.
