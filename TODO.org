* Todo [0/8]
- [ ] Have the ~louis~ binary depend on the ~louis~ library instead of
  compiling the same sources again
  - ~src/main.rs~ declares its own ~mod parser~, ~mod translator~,
    ~mod metadata~, ~mod test~ and ~mod yaml~; ~src/lib.rs~ declares an
    overlapping ~mod parser~, ~mod translator~, ~mod emphasis~ and
    ~mod hyphenation~. Both targets therefore compile the same sources,
    and to the compiler the resulting types are unrelated: the
    binary's ~parser::TableError~ is not the library's.
  - Consequences visible today:
    - ~main.rs~'s ~TableLoadError~ is a variant-for-variant copy of
      ~lib.rs~'s public ~TranslationError~, and cannot simply use it
    - dead-code warnings differ between the two builds, so the same
      function is "never used" in one target and used in the other,
      which makes the warnings hard to act on (see
      ~with_display~/~DisplayTable::compile~)
    - anything the CLI needs has to exist twice or be duplicated
  - The blocker is deciding what becomes public API. The CLI reaches
    for ~parser::table_expanded_in~, ~TranslationPipeline~,
    ~ResolvedTranslation~, ~AnchoredRule~ and ~TranslationStage~, none
    of which ~lib.rs~ exports today, and the library API is explicitly
    not stable yet. Same question as exposing a display table on
    ~Translator~.
- [ ] Implement the ~syllable~ opcode with boundary checking
- [ ] Cursor handling
- [ ] The boundary functions (~word_start~, etc) only work in forward
  translation — confirmed ~uppercase.rs~ has no backward-direction
  logic at all; likely the same root cause behind the backward-caps
  gaps under "Known gaps" below
- [ ] Normalize input text to a canonical Unicode form
  - NFC normalization was tried (input at the start of the pipeline,
    plus rule patterns) but reverted: it fixed tables that define
    rules for precomposed characters (e.g. pt-pt-g1.utb), but broke
    tables that define rules for standalone combining characters (IPA,
    Hebrew, Yiddish) with no table-side workaround available. No
    normalization happens today. NFD normalization is a promising
    alternative — it decomposes all input, so combining marks stay
    explicit and precomposed rules still match via longer trie paths.
  - See ADR in [[file:doc/Architecture_Decision_Records.org][Architecture Decision Records]]
- [ ] performance
  - put translations into offset buckets
  - measure performance
  - reduce the regexp opcode operand to only 32 bit
  - [-] handing out references instead of cloning stored translations
    was tried and *measured to be pointless*, 2026-09-03. The premise
    was that a ~ResolvedTranslation~ is 288 bytes of which 184 are its
    ~Option<AnchoredRule>~ (a ~Rule~ is 152 and carries ~String~s), and
    that the trie clones one per candidate for every node along the
    match path at every input position
    (~find_translations_from_node~, ~src/translator/trie.rs~).
    - upper-bound experiment: store no origin at all in the trie, so a
      candidate clone skips the rule entirely -- strictly more saving
      than ~Cow~ would give, since ~Cow~ still clones the computed
      candidates. Doing *less* work measured 2% *slower* on
      ~benches/translate.rs~ (word 188.7µs → 193.0µs, sentence 2.127ms
      → 2.181ms, paragraph 13.95ms → 14.19ms) and identical on
      ~check da-dk-g28-dictionary_harness.yaml~ (6.63/6.82s → 6.75/6.68s).
      Two workloads on purpose: the criterion bench is regexp-dominated
      by design (964 ~match~ rules in en-ueb-g2), the dictionary
      harness leans on the trie. Neither can see the clone.
    - so don't do this for the clone's sake. If it is ever wanted for
      another reason, the shape is: tables keep owning their
      translations and hand out ~&ResolvedTranslation~ (no lifetime on
      the stored type, so no self-reference), but the candidate list is
      mixed -- trie and display candidates are stored, ~match~/~context~
      ones are built per match from ~Translation::Unresolved~ via
      ~resolve(capture, ..)~, and the indicator modules derive theirs
      per position -- so the collectors want
      ~Cow<'_, ResolvedTranslation>~.
  - [X] keep the values of maps consulted per character small. What
    cost ~12% on the YAML suite when ~DisplayTable~ started storing
    whole translations was not the cloning but the *value size*:
    widening ~HashMap<char, char>~ (4-byte values, ~1KB) to
    ~HashMap<char, ResolvedTranslation>~ (288-byte values, ~73KB for
    ~unicode.dis~) turns a per-character lookup into a cache miss, over
    2.2M assertions. Fixed by boxing the rule in the value, which is 16
    bytes. Interleaved, four ways: baseline without rules 58.2s, inline
    translations 65.3s, small value plus a ~Vec~ indexed by ~usize~
    57.9s, boxed rule 58.7s -- so how the value is shrunk does not
    matter, only that it is.
- [ ] Make the suite reproducible: ~TrieNode::transitions~ is a
  ~HashMap~, so a tie between candidates is decided by iteration order,
  which is randomized per process. ~pa.yaml~, ~hi_harness.yaml~ and
  ~fr-bfu-g2.yaml~ report different numbers between runs of the same
  binary, which is the size of a real regression. A ~BTreeMap~ fixes it
  in ~4 lines and measured faster; see the ADR "Rule selection does not
  depend on table order" for why we freeze an arbitrary order rather
  than adopt liblouis's definition order, and for the linter idea that
  would find the underlying table ambiguities.
- [ ] Expose the library via a C ABI so it can be used from other
  languages (see [[https://github.com/mozilla/cbindgen][cbindgen]] or [[https://github.com/rust-diplomat/diplomat][Diplomat]])

* Known gaps
- [ ] Two ~match~ rules of equal rank: we pick the last defined,
  liblouis the first
  - This is the forward half of the ~afr-za-g2~ cluster — 186 of that
    file's 2663 real failures. See the "sub-case where the weights are
    equal" under the ADR "Match-rule candidate selection: weight vs.
    table-definition order" for the full analysis and what a fix needs.
  - Reduced to the two competing rules from ~afr-za-g2.ctb~ (lines 143
    and 274), translating "algemene":
    #+begin_src
    # spell-out rule first, as in the real table -> we pick the catch-all (wrong)
    noback match [BbMmSs] en [Ee]%[^_.] 15-1345
    noback match !%3 en !%3 26                     ->  ⠁⠇⠛⠑⠍⠢⠑

    # same two rules, order swapped -> we pick the spell-out (correct)
    noback match !%3 en !%3 26
    noback match [BbMmSs] en [Ee]%[^_.] 15-1345    ->  ⠁⠇⠛⠑⠍⠑⠝⠑
    #+end_src
    Either rule alone produces the correct output, so both patterns are
    fine; only the choice between them is wrong. That the order matters
    at all proves the two rank equally — otherwise ~max_by_key~ would
    pick the same rule either way — and on a tie it returns the last
    candidate, which follows table order.
- [ ] Backward: lower-sign contraction cells satisfy a ~word~ rule's
  space-or-punctuation boundary
  - This is the backward half of the same ~afr-za-g2~ cluster: 2477 of
    its 2663 real failures.
  - Afrikaans's "lower sign group" contractions occupy the same dot
    patterns as punctuation, which ~afr-za-g2.ctb~ inherits through
    ~afr-za-g1.ctb~ → ~en-ueb-g1.ctb~ → ~en-ueb-chardefs.uti~:
    | contraction        | punctuation      | cell |
    |--------------------+------------------+------|
    | ~midword aa 2~     | ~punctuation , 2~ | ⠂    |
    | ~begmidword on 25~ | ~punctuation : 25~ | ⠒    |
    | ~begmidword te 235~| ~punctuation ! 235~| ⠖    |
    | ~begword deur 256~ | ~punctuation . 256~| ⠲    |
  - ~Rule::Word~ (~src/translator/table/primary.rs~) inserts with
    ~Transition::Start~/~End~ of ~[Space, Punctuation]~ — a *positive*
    requirement, unlike ~partword~'s letter lookaround. In backward
    translation those transitions are resolved against ~dots_classes~,
    so a neighbouring ⠂ counts as the comma and the word boundary is
    spuriously satisfied. Every single-cell ~word~ contraction then
    fires mid-word. 1823 of the 2477 failures contain ⠂ alone.
  - Note this is *not* fixed by seeding the letter dots class (see the
    entry below): ~word~ asks "is the neighbour space or punctuation",
    not "is the neighbour a letter", so adding letters changes nothing.
  - The second symptom of the same collision is a lower-sign cell
    decoded as the punctuation itself: ~⠐⠣⠲⠐⠜~ → "(.)" rather than
    "(deur)".
  - Reproducer, and the discriminator that pins the mechanism:
    #+begin_src yaml
    display: unicode-without-blank.dis
    table: afr-za-g2.ctb
    flags: {testmode: backward}
    tests:
      # ⠅ is letter k and `word kan`; both cases end a longer word
      - [⠍⠂⠅, maak]   # FAILS: "myaakan" — ⠂ before it has the comma's dots,
                       #        so `word my` and `word kan` both fire
      - [⠃⠕⠑⠅, boek]  # passes — ⠑ is a plain letter, no collision
      - [⠌⠂⠞, staat]  # FAILS: "stilaatot" — `word stil` and `word tot`
      - [⠃⠗⠂⠊, braai] # FAILS: "briefaais" — `word brief` and `word is`
    #+end_src
    ~boek~ passing while ~maak~ fails is the whole diagnosis: the only
    difference is whether the preceding cell's dots collide with a
    punctuation definition.
  - Same family as the two entries below — a backward boundary check
    classifying a dot pattern instead of asking what the cell is at
    this position — so the real fix is likely shared with them.
- [ ] ~letsign~ is unhandled in both directions, and its dots collide
  with multi-cell letter definitions
  - ~da-dk-g28.ctb~ line 870 declares ~letsign 56~, but dots 56 is
    *also* the lead cell of that table's two-cell letter definitions:
    #+begin_src
    lowercase q 56-12345    lowercase x 56-1346     lowercase à 56-12356
    lowercase w 56-2456     lowercase z 56-1356     lowercase ç 56-12346
    #+end_src
    so a leading ⠰ is genuinely ambiguous — letter sign, or first half
    of a ~q~/~w~/~x~/~z~.
  - *Forward* (312 of the 324): a letter immediately followed by a
    digit takes the letter sign; we emit none. liblouis treats a digit
    as a word boundary for letter-sign purposes and
    ~src/translator/indication/lettersign.rs~ does not. The remaining
    3 are two-letter words (~ii~, ~ik~).
  - *Backward* (1031 of the 1032): the letsign/two-cell-letter
    ambiguity is resolved inconsistently, and position-dependently.
    ⠰ as a letter sign is never dropped, and ⠰ as a lead cell resolves
    in some positions but not others.
  - Reproducers, both runnable as-is against the real table:
    #+begin_src yaml
    # forward: a letter against a digit takes the letter sign
    display: unicode-without-blank.dis
    table: da-dk-g28.ctb
    flags: {testmode: forward}
    tests:
      - [a1, ⠰⠁⢁]        # FAILS: ⠁⢁
      - [a500, ⠰⠁⢑⢚⢚]    # FAILS: ⠁⢑⢚⢚
    #+end_src
    #+begin_src yaml
    # backward: same dots, four positions, three different outcomes
    display: unicode-without-blank.dis
    table: da-dk-g28.ctb
    flags: {testmode: backward}
    tests:
      - [⠰⠭⠽⠇⠕⠋⠕⠝, xylofon]  # passes — two-cell x at word start
      - [⠞⠁⠰⠭⠊, taxi]          # passes — two-cell x mid-word
      - [⠕⠰⠭⠊⠙, oxid]          # FAILS: "opxid" — two-cell x mid-word
      - [⠁⠰⠭, ax]               # FAILS: "atx"   — two-cell x at word end
      - [⢚⠰⠊, 0i]              # FAILS: "0¨i"   — no 56-24 letter exists,
                                #                 so ⠰ can only be letsign
    #+end_src
    ~taxi~ passing while ~oxid~ and ~ax~ fail is the useful clue: the
    two-cell path works, so this is about how the ambiguity is resolved
    per position, not a missing definition.
  - There is precedent for the backward half. The same collision shape
    was solved for ~capsletter~/~numsign~ against a real letter in the
    Malayalam and Punjabi tables — an opcode is only recognized as an
    indicator when its dots aren't already claimed by a real letter.
    Extending that check to ~letsign~, where the claimant is a
    *multi-cell* definition rather than a single cell, is the likely
    shape of the fix.
  - Not part of this: 6 forward failures where an all-caps word takes a
    word contraction instead of being spelled out (~AF-kontor~ →
    expected ~⡁⡋⠤⠅⠕⠝⠞⠭~, actual ~⡴⠤⠅⠕⠝⠞⠭~) and 1 backward
    equivalent (~⡙⠝⠅~ → "Dnk" rather than "Danmark").
- [ ] Backward word-boundary checks ask about a cell, not a position
  - Both sides of a backward boundary check are evaluated against the
    braille input via ~dots_classes~ (~PrimaryTable~'s ~trie_ctx~,
    ~src/translator/table/primary.rs~). liblouis is asymmetric
    (~lou_backTranslateString.c~):
    - the *before* side reads the last character of the output
      produced so far and classifies it with the text classes
      (~back_setBefore~, ~isBegWord~ — "look at what has already been
      translated")
    - the *after* side reads the next braille cell and classifies it
      with the dots classes, but when that cell is not a letter by
      attribute it walks the rules attached to the cell and treats any
      rule with ~charslen > 1~ as word-continuation (~isEndWord~,
      excluding ~begword~/~midword~ per liblouis#360)
  - So liblouis never needs contraction dots in its letter class. We
    approximate that rule walk by pre-seeding ~dots_classes~ from
    every all-alphabetic contraction opcode (~TableContext::compile~,
    ~src/translator/table.rs~). That has now been widened three times
    for three opcode families (edf1b4c, bed6112, and the ~partword~
    fix), and it still has a ceiling:
    - the guard is narrower than liblouis's ~charslen > 1~, so a
      contraction spelling non-letters still breaks a neighbouring
      ~partword~. Reproducer: a table with ~always n't 12356~ and
      ~partword ed 1246~ translates "can'ted" forward but
      back-translates ~⠉⠁⠷⠫~ to "can't" plus a hex fallback
    - the property is per-cell and global, so a cell counts as a
      letter at every position, not only where a contraction applies
    - "a translation continues the word here" is not "this cell is a
      letter", but the letter class is the only way we can say it, so
      the cell also reads as a letter to number/punctuation boundary
      checks, ~before~/~after~ class constraints and the
      capitalization tiers. Over-application this way is what
      regressed the suite in earlier attempts
    - the before side cannot be fixed this way at all: its correct
      answer depends on the text already produced, which no property
      of a cell can encode (an indicator cell emits no text, so
      liblouis's output-side lookup sees past it while ours sees the
      indicator)
  - Fixing it properly means matching liblouis's split: text classes
    over produced output for the before side, dots classes plus a rule
    walk for the after side. Widening the guard only moves the ceiling.

- [-] ~Attribute::Boundary~/~ByOrder~/~Any~ (the attributes inside a
  rule's ~%[...]~/~$...~ set) are mostly no-ops

    the word/group-sign gap below)
  - [ ] ~ByOrder~/~Any~ in match_pattern.rs, and all three in
    context_pattern.rs, remain no-ops
  - Note on reading ~%[...]~: the bracket contents are a *union* of
    attributes, not a character set and never a negation
    (~pattern.c~'s ~compileAttributes~): ~_~ space, ~#~ digit, ~a~
    letter, ~u~ uppercase, ~l~ lowercase, ~.~ punctuation, ~$~ sign,
    ~m~ math, ~~~ seqdelimiter, ~<~/~>~ seqbefore/after, ~0~-~7~ the
    numbered attributes, and ~^~ *end of input*. So ~%[^_]~ reads
    "boundary or space" and ~%[^_.]~ "boundary, space or punctuation" —
    both word-boundary tests. ~^~ inside the brackets is not negation;
    only a leading ~!~ negates.
