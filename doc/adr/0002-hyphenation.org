* ACCEPTED ADR-0002: Hyphenation
- Deciders :: CE
- Date :: [2026-08-20 Thu]

** Context and Problem Statement

Liblouis uses hyphenation dictionaries from the TeX project to provide
some functionality in the form of the ~nocross~ opcode prefix. It
would be nice if we could use off-the-shelf functionality instead of
having to re-implement this as in the C version.

The [[https://crates.io/crates/hyphenation][hyphenation crate]] makes it fairly easy to use a dictionary. It
comes pre-configured with [[https://github.com/tapeinosyne/hyphenation/tree/master/dictionaries][a lot]] of TeX and OpenOffice hyphenation
dictionaries. These come not in their standard form but are encoded
using the bincode format. This encoding happens during the build
process of the hyphenation crate, where all the [[https://github.com/tapeinosyne/hyphenation/tree/master/patterns][pattern files]] in
the ~patterns~ directory are ecoded and stored in the ~dictionaries~
directory.

I added the 3 relevant dictionaries from liblouis, namely
~da-dk-g2.dic~, ~de-g1-core-patterns.dic~ and
~de-g2-core-patterns.dic~ to the patterns folder of hyphenation, added
the files to ~build.rs~ and ~hyphenation_commons/src/language.rs~ and
finally built the hyphenation crate with

#+begin_src shell
  cargo build --features build_dictionaries
#+end_src

The liblouis dictionary files were encoded and I grabed them out of
~target/debug/build/hyphenation-4f7fc3b4af290d85/out/dictionaries~.

You can now load this dictionary and hyphenate words:

#+begin_src rust
  use std::error::Error;

use hyphenation::Load;
use hyphenation::{Hyphenator, Language, Standard};

fn main() -> Result<(), Box<dyn Error>> {
    let path_to_dict = "/path/to/da-g2.standard.bincode";
    let en_us = Standard::from_path(Language::Dutch, path_to_dict)?;

    let hyphenated = en_us.hyphenate("bestemmer");
    println!("Hello, {:?}!", hyphenated);

    Ok(())
}
#+end_src

which results in

#+begin_src shell
cargo run
Hello, Word { text: "bestemmer", breaks: [7] }!
#+end_src

You'll notice that I used the language ~Language::Dutch~. The
language ~DanishGrade2~, that I had added to my local version of the
~hyphenation_commons~ crate, does not exist when I use the
~hyphenation~ crate from crates.io. If I use ~Language::EnglishUS~ it
compiles but complains and tells me the the dictionary is in for the
~Language::Dutch~.

The problem is that the ~hyphenation_commons~ crate converts the list
of languages to an enum that is baked into the build. There does not
seem to be a way to load a dictionary with out the ~Language~ enum.
The bincode seems to contain the language in its serialized data
structure.

At the moment it definitely looks like there is more research needed
as to how we could use the hyphenation crate using our own
dictionaries. Maybe we'll have to rip out the relevant parsing code
from ~hyphenation_commons~ and then provide the hyphenator with a
deserialized version of that.

*** Update: the crate route was abandoned

The enum-baking problem above never got resolved cleanly, and it kept
being the wrong shape for our use case: liblouis dictionaries are
identified by table path like every other liblouis table, not by a
closed set of languages known at the crate's own build time. Since all
we actually needed from the ~hyphenation~ crate was its Knuth-Liang
pattern-matching algorithm — not its bundled TeX/OpenOffice pattern
corpus, and not its print-text case-folding — that algorithm was
reimplemented natively in ~src/hyphenation.rs~, parsing liblouis's own
~.dic~ pattern-file format directly. There is no external crate and no
build-time bincode conversion step; a hyphenation table loads and is
identified exactly like any other liblouis table.

** Considered Options

** Decision Outcome

Chosen option: a native Knuth-Liang implementation in
~src/hyphenation.rs~, wired into table loading (~IncludeHyphenation~)
and used to filter ~nocross~ candidates: a candidate contraction is
only offered if the hyphenator does *not* find a break point inside
it.

Correctness is verified, not just integrated: the native
implementation was checked byte-identical to the old
~hyphenation~-crate-based behaviour across liblouis's full YAML test
suite (278k test cases across the en-g3 and da-dk-g26 dictionaries),
and the previously-~#[ignore]~d ~nocross~ unit test in
~primary.rs~ now passes.

** Positive Consequences

- No external dependency, no build-time bincode conversion step, and
  no crate-side enum of supported languages to patch and rebuild
  out-of-band — a hyphenation dictionary is just another liblouis
  table, identified by path.
- Verified byte-identical to the crate-based behaviour it replaced
  across liblouis's full YAML test suite, so the switch carried no
  regression risk.

** Negative Consequences

- We now own the pattern-matching algorithm ourselves instead of
  depending on a maintained crate, though it verified out at parity
  with the crate's implementation and is small in scope.
- ~nocross~'s use of hyphenation is still a coarser check than
  liblouis's: it asks whether the matched candidate substring has any
  break anywhere, rather than liblouis's positional check of whether a
  break falls inside *that candidate's span* within the enclosing
  word. This predates the native rewrite (the old
  ~hyphenation~-crate-based check was exactly as coarse) and isn't
  caused by it; tracked separately in ~TODO.org~ under "Known gaps".
