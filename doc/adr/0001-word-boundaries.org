* ACCEPTED ADR-0001: Handle word boundaries
- Deciders :: CE
- Date :: [2024-03-08 Fri]

We need a way to handle word boundaries, as some rules only apply at
specific boundaries. Currently the trie does not account for any
boundaries.

** Context and Problem Statement

When given an input we have to look for a matching translation rule.
This is in some ways similar the process inside a regex engine.
However in our case mostly have consuming transitions between the
nodes. Only at the beginning and at the end of a match we can have
non-consuming word-boundary matches. This simplifies the process quite
a bit as in most cases we do not have to search through multiple
branches.

** Decision Drivers

- start with the simplest solution
- move as much processing from the translation to the compilation
  stage

** Considered Options

- Handle different contexts with separate tries :: Leave the trie code
  as is and handle the context using multiple tries with wrapper code
- Enhance trie with transitions :: Add transitions to the trie that
  map to non-consuming word boundaries
- Filter the candidates found in the trie :: Leave the trie as is and
  just filter the returned candidates.

** Decision Outcome

Chosen option: "Enhance trie with transitions", because it keeps a
single search structure instead of splitting rules across multiple
tries or computing candidates first and filtering them afterwards.
Boundaries are modelled as non-consuming transitions alongside the
normal character transitions, so a boundary check is just another
edge to follow during the same trie walk.

This turned out to generalize well: the same non-consuming-transition
idea was later reused for the liblouis ~before~/~after~
class-constraint keywords, which are a lookbehind/lookahead against a
character class rather than a fixed boundary condition.

*Update (2026-08-19):* the concrete ~Boundary~ enum described above
did not survive. It checked the wrong pair of characters — the
matched rule's own edge character in addition to the true neighbor —
which was harmless for letter-based rules (the gate always passed)
but wrong for punctuation. ~Boundary~ and the whole
~is_word_start~/~is_word_end~ family of predicates were deleted in
commit 96035dd; the non-consuming-transition *idea* survived and was
generalized instead into ~Transition::Start~/~End(Vec<CharacterClass>)~,
a direct lookbehind/lookahead against the real neighbor that now
serves both the opcode-intrinsic boundary checks and the
~before~/~after~ keyword through one mechanism. Separately,
~prepunc~/~postpunc~ turned out not to fit a trie transition at all —
liblouis implements them via a variable-length outward scan, not a
single-neighbor class check — and were moved to a dedicated
~PunctuationConstrainer~ checked post-hoc in ~trace()~, outside the
trie entirely. See the linked follow-up ADR for the full analysis.

** Positive Consequences

- One trie handles both boundary-constrained and unconstrained rules;
  nothing to keep in sync across parallel structures.
- The non-consuming-transition mechanism generalized to other
  lookbehind/lookahead needs (the ~before~/~after~ keywords) without
  changing the trie's overall shape.

** Negative Consequences

- All boundary conditions are checked at every character position,
  even when the current node has no boundary transitions to offer.
  This is a performance cost that has not yet been benchmarked against
  lazier evaluation.
- Non-consuming transitions make the trie a less pure prefix tree: a
  lookup can branch without consuming input, which is a bit more to
  hold in your head than plain character-by-character descent.

** Pros and Cons of the Options

***  Handle different contexts with separate tries

- Bad :: rules unconstrained by any boundary would need to be
  duplicated across every context-specific trie, or looked up
  separately and merged, reintroducing the synchronization problem
  this option was meant to avoid

***  Enhance trie with transitions

- Good :: unifies the search for candidates
- Bad :: makes the trie more complicated

***  Filter the candidates found in the trie

- Good :: No change needed in the trie
- Bad :: Processing during translation
