* ACCEPTED ADR-0010: Unify word/number-boundary checks onto class-constraint lookaround
- Deciders :: CE
- Date :: [2026-08-18 Tue]
- Implemented :: [2026-08-19 Wed]

** Context and Problem Statement

~midword ! ⠠⠖~ fires on an isolated ~"!"~ with nothing around it,
producing ~⠠⠖~ instead of ~⠖~. Cause: ~Rule::Midword~ compiles to
~Boundary::NotWord~ transitions, evaluated by
~is_word_start~/~is_word_end~. ~is_word_start~ gates on ~is_word(c)~
before ever consulting the true preceding character, so for a rule
whose own text isn't a letter, the gate fails and the check
degenerates to "always true" regardless of what actually precedes the
match — the true neighbor is never consulted. Correct by accident for
ordinary letter-based rules (gate always passes), wrong for
punctuation.

liblouis itself computes ~beforeAttributes~/~afterAttributes~ from
~input->chars[pos-1]~ and ~input->chars[pos+length]~. Every
word/number opcode reduces to one shape, "does the real neighbor's
attributes intersect a required set", differing only in which set
(Letter, Space, Punctuation, Digit, SeqDelim):

| Opcode       | before                            | after                             | combine    |
|--------------+-----------------------------------+-----------------------------------+------------|
| ~word~       | Space,Punctuation                 | Space,Punctuation                 | AND        |
| ~begword~    | Space,Punctuation                 | Letter                            | AND        |
| ~begmidword~ | Letter,Space,Punctuation          | Letter                            | AND        |
| ~midword~    | Letter                            | Letter                            | AND        |
| ~midendword~ | Letter                            | Letter,Space,Punctuation          | AND        |
| ~endword~    | Letter                            | Space,Punctuation                 | AND        |
| ~partword~   | Letter                            | Letter                            | *OR*       |
| ~sufword~    | Space,Punctuation,SeqDelim        | Space,Letter,Punctuation,SeqDelim | AND        |
| ~prfword~    | Space,Letter,Punctuation,SeqDelim | Space,Punctuation,SeqDelim        | AND        |
| ~begnum~     | Space,Punctuation                 | Digit                             | AND        |
| ~midnum~     | Digit                             | Digit                             | AND        |
| ~endnum~     | Digit                             | —                                 | —          |
| ~decpoint~   | Digit                             | Digit (required)                  | reclassify |

~word~ uses ~Boundary::Word~ in our code, same gate bug and
same-too-broad-neighbor-set issue as noted below. ~decpoint~ doesn't
go through ~Boundary~ at all in either engine's sense we've been
discussing — liblouis reclassifies it to ~midnum~ on the spot if a
digit precedes; our own ~Decpoint~ arm skips the trie boundary
mechanism entirely and instead tags the character for the numeric
indicator/constrainer as if it were a ~midnum~ character. No live bug
there, just a different existing mechanism — not part of this ADR's
fix.

liblouis is fine-grained and table-driven (most sides are a union of
classes, not one "word-ness" bit). Our ~Boundary~ enum's bug is
checking the wrong pair (neighbor *and* the rule's own edge character)
instead of the neighbor alone.

An enhanced ~Boundary~ checking only the real neighbor would be
sufficient — and structurally identical to the ~ClassConstraint~/
~StartClass~/~EndClass~ mechanism already used for ~before~/~after~
(the "Handle word boundaries" ADR already flags this reuse). The one
gap shared by both mechanisms today: most opcodes need a class *union*
(~Space,Punctuation~ etc.), which neither expresses directly —
~Boundary~ hardcodes one variant per union, ~ClassConstraint~ only
ANDs.

~midnum~ and ~endnum~ share the same bug. It only manifests when the
matched rule's own text shares the class being tested for.

~begnum~ already sidesteps half the problem: its "before" side uses
~Boundary::AfterSpaceOrPunct~, a genuine lookbehind-only check on the
real neighbor that never touches ~c~.

Confirmed which opcodes our ~Boundary~ mechanism is actually wired to
(by reading every ~insert()~ call in ~primary.rs~): twelve of the
thirteen above (~decpoint~ excepted, per the note), plus four more —

~joinword~, ~lowword~, ~prepunc~ and ~postpunc~ are implemented in
liblouis via a *scan* (~onlyLettersAhead~, an outward scan) and we
currently approximate with a plain ~Boundary~ check. No
single-neighbor class lookup expresses a scan — these four need their
own follow-up.

** Decision Drivers

- Don't maintain two differently-coded mechanisms for the same
  non-consuming-lookaround idea
- Fix the actual bug (wrong pair of characters checked) *and* the
  per-opcode set precision, not just the one opcode with a failing
  test
- Minimize regression risk: most passing tests exercise letter-based
  rules
- Reuse ~ClassConstraint~ if possible
- Don't conflate this with the four scan-based opcodes
  (~joinword~/~lowword~/~prepunc~/~postpunc~), which need a different
  fix entirely

** Considered Options

1. *Narrow fix only* — fix ~midword~ alone via ad hoc
   ~class_constraints~, leave ~Boundary~ and the rest of the family
   as-is. Minimal and safe; leaves the same bug live in the other
   eleven single-neighbor opcodes.

2. *Fix the whole single-neighbor family* — re-express all twelve
   opcodes above as ~ClassConstraint~s with their correct sets,
   retiring ~is_word_start~/~is_word_end~/~is_number_start~/
   ~is_number_end~ for these opcodes. Needs class-union support
   first. The four scan-based opcodes are untouched either way.

3. *Full consolidation* — add class-union support, re-express every
   remaining ~Boundary~ variant (Punctuation/WordPunctuation/
   PunctuationWord, used by the scan-based opcodes) as
   class-constraints too, delete ~Boundary~ entirely. Doesn't
   actually fix the scan-based opcodes' real gap (they'd still be
   approximations, just with a different-shaped primitive
   underneath) — so this buys mechanism uniformity, not correctness,
   for those four.

4. *Status quo* — no change beyond Bug B's narrow fix; leave the
   wider question open.

** Decision Outcome

Chosen option: *2*. ~Boundary~ and every
~is_word_start~/~is_word_end~-family predicate are deleted;
~Transition::StartClass~/~EndClass~ were generalized in place to
~Start~/~End(Vec<CharacterClass>)~, giving class-union support via
~.any()~ across the vec — the same type now serves both the
opcode-intrinsic checks in the table above and the ~before~/~after~
keyword, closing the "two mechanisms" gap this ADR was written about.

One subtlety surfaced only during implementation, not analysis: a
missing neighbor (true start/end of input) must satisfy exactly the
~Space~ requirement directly (~*class == CharacterClass::Space~ on
~None~), not a substituted placeholder character.

Confirms option 3's premise directly: deleting ~Boundary~ for the
scan-based opcodes bought nothing for them. Re-pointing ~prepunc~/
~postpunc~ at the new ~Vec<CharacterClass>~ mechanism (still a
~Start[Space]~/~End[Space]~ approximation, no scan) made their
approximation *worse* than the old ~Boundary~-based one. Decided to
accept this rather than block the rest of the fix on it: the test is
disabled rather than asserting the wrong behavior. The real fix,
liblouis's actual scan, is tracked as a follow-up.

*Follow-up implemented:* ~prepunc~/~postpunc~ now get liblouis's real
scan via a dedicated ~PunctuationConstrainer~, computed once per input
like ~HyphenationConstrainer~ — not a trie transition at all, since
the scan is variable-length (forward/backward past further
punctuation to a letter or digit, stopping at whitespace), which
~Transition::Start~/~End~ structurally can't express. The trie insert
for both opcodes now carries no boundary; eligibility
is gated post-hoc in ~trace()~ by matching the candidate's origin rule
against ~constraints.prepunc_ok_at()~/~postpunc_ok_at()~.
