* ACCEPTED ADR-0016: Rule selection ranks by what the rules say, then by definition order
- Deciders :: CE
- Date :: [2026-11-10 Tue]

Revised. The first version ([2026-09-03 Thu]) held that a tie between
candidates is an ill-formed table and declined any tie-break by table
order; see "History" below.

** Context and Problem Statement

At each position several rules can match, and one has to be applied.
louis-rs ranked candidates by what the rules themselves say: consumed
length, then weight (length plus the ~before~/~after~ context the rule
checked). Whatever that left undecided was decided by accident:

- Candidates that tied on rank were picked by ~max_by_key~, which
  returns the last of them, in the order the trie's map happened to
  yield them. With a ~HashMap~ that varied per process (~pa~, ~hi~,
  ~fr-bfu-g2~ swung by about ten tests per run); a ~BTreeMap~ froze an
  arbitrary order.
- Rules with the same input and boundaries share a trie node, and a
  node held only one of them. Which one was decided at compile time,
  by a precedence comparison that only ever compared against the
  default, so in effect the last-defined rule won. If that rule then
  failed a check in ~trace()~ (a ~prepunc~ mid-word, say), nothing was
  left to fall back on.

liblouis decides the same questions by the order of its rule chains
(~compileTranslationTable.c~):

- multi-character chains: longer rules first, then everything else
  before ~always~, then definition order
- single-character chains: character definitions (~CTO_Space~ ..
  ~CTO_UpLow~) last, otherwise definition order
- backward chains: by output length
- pass rules: by the length of the literal their test starts with
  (~passFindCharacters~), then definition order; the first rule that
  matches wins, without comparing what it consumes
- and in every chain the first rule that validates is taken, so a rule
  rejected by its context check hands over to the next one

Tables are written against this behaviour. The ~ta~, ~ml~, ~pa~ and
~hi~ tables include ~en-in-g1.ctb~ and override its ~word , 4-2~ with
an earlier ~always , 2~; ~afr-za-g2.ctb~ puts a specific ~match~ rule
before a catch-all one; ~vi-lettersdef.uti~ is included before the
~vi-puncsdef.uti~ rule that would otherwise undo its precomposition.

** Decision Drivers

- The rules' own content comes first. A longer match, or one that
  checked more context, is more specific, whatever its position.
- Parity with liblouis: tables are written and tested against its
  behaviour, and the ties are not rare (an earlier diagnostic found
  414 occurrences in 14 tables, see "History").
- Determinism must not depend on a data structure's iteration order.
- Relying on the position of a rule in a file is brittle, so it should
  be the last resort, not a principle.
- The whole policy should be readable in one place.

** Considered Options

1. Keep the first version: ties are table bugs, fixed upstream; the
   engine only makes them reproducible.
2. Adopt liblouis's chain order as the whole policy.
3. Rank by the rules' content first, then by liblouis's chain-order
   keys, with definition order last.

** Decision Outcome

Chosen option: 3. Every matching rule stays a candidate: trie nodes
keep all the rules that land on them, and the choice is made among the
candidates that pass ~trace()~'s checks, so a rejected rule hands over
to the next one, as in liblouis. Candidates then compete on ~Rank~
(~src/translator/translation.rs~), a struct whose derived ordering
compares its fields in declaration order, the highest winning:

| Field              | Meaning                                                      | Source                      |
|--------------------+--------------------------------------------------------------+-----------------------------|
| ~zero_length~      | a candidate that consumes nothing goes first                 | louis-rs                    |
| ~length~           | characters consumed                                          | louis-rs, liblouis          |
| ~weight~           | length plus the ~before~/~after~ context checked             | louis-rs                    |
| ~literals~         | literal characters in a pass or ~correct~ test               | liblouis's pass-rule sort   |
| ~precedence~       | character definition < indicator < ~always~ < other rules    | liblouis's chain order      |
| ~output_length~    | backward main stage only: the longer output                  | liblouis's backward chains  |
| ~nocross~          | a ~nocross~ rule beats its plain twin                        | louis-rs                    |
| ~definition_order~ | the earliest-defined rule                                    | liblouis                    |

- ~Precedence~ is derived from the rule, not stored. A one-character
  ~always~ counts as an ordinary rule, since liblouis only puts
  ~always~ last in its multi-character chains.
- Definition order is a rule's position in the list a table is
  compiled from, across ~include~ files and table lists, stamped by
  ~parser::in_definition_order~.

Option 2 was measured: dropping weight in favour of liblouis's order
alone churned results (~en-g3~ lost 184 tests, ~tr~ and ~da~ gained
about 90), so weight stays ahead of the chain-order keys.

*** Positive Consequences

- Deterministic by construction: only candidates from the same rule
  can tie, and those produce the same output. Two suite runs with a
  ~HashMap~ for the trie's transitions were identical; the ~BTreeMap~
  stays only because it compiles faster.
- 909 fewer failures across the suite and no file worse. Most of it is
  in ~ta~/~ml~/~pa~/~hi~ (622), largely the ⠈-before-punctuation
  cluster; also
  ~fa-ir-g1~ (38, now 0), ~en-ueb-g2-dictionary_harness~ (61),
  ~sw-ke~ (25), ~afr-za-g2~ (15), ~vi~ (5) and the ~en-ueb~ backward
  numeric space (5).
- The policy is one struct, with each field documented and the
  precedence of the fields visible in their order.

*** Negative Consequences

- Table order now matters, as in liblouis: reordering two rules that
  nothing else separates changes the output. Such tables still
  deserve fixing upstream, and the engine no longer surfaces them (see
  "Deferred: a table linter").
- Where weight decides before the chain-order keys, louis-rs can still
  differ from liblouis. Backward ~decpoint~ cannot get its "digit
  follows" check, which would add weight and beat an earlier
  same-dots ~always~ (~TODO.org~).
- Known divergences that remain: liblouis does not compare consumed
  length between pass rules, and tries ~context~ rules without a
  leading literal before all others (~findForPassRule~ in
  ~lou_translateString.c~). Neither is modelled.
- A ~_N~ lookback that rewinds past the start is not checked, which
  the old last-defined accident hid; ~multipass-forward.yaml~ and
  ~multipass-backward.yaml~ now fail that test (~TODO.org~).

** Deferred: a table linter

Rules that only definition order separates are still worth reporting
upstream: they are fragile in liblouis too. A linter would find them
without needing input:

- trie rules are cheap: group by ~chars~ and report pairs with
  different dots whose positional constraints can co-occur
  (~begmidword~ overlaps ~midword~; ~word~ and ~endword~ do not)
- ~match~/~context~ rules need pattern intersection. It is decidable
  on the NFA the regexp VM already builds -- product construction plus
  an emptiness check -- but it is real work
- the collisions observed are mostly the cross-engine kind (~match -
  te ... ⠞⠑~ against ~begmidword te ⠖~), so a trie-only linter would
  miss the interesting ones

It would share machinery with the rule-level coverage tool
([[file:0014-rule-level-coverage-tool.org][ADR-0014]],
[[https://github.com/liblouis/louis-rs/issues/27][issue #27]]), which
already knows which rule fired where.

** History

The first version (2026-09-03) was written to fix the suite's
nondeterminism. It argued that rules are best understood as a union of
regular expressions, that POSIX's leftmost-longest needs no positional
tie-break, and that two candidates tying on length and weight are
therefore an ill-formed table, to be fixed upstream. It adopted the
~BTreeMap~ for reproducibility and declined definition order, and
[[file:0008-match-rule-candidate-selection.org][ADR-0008]] reversed its own
earliest-defined proposal to match.

A diagnostic at the selection site then counted the ties where the
candidates disagree about the output: 114 distinct rule sets, 414
occurrences, in 14 tables (~afr-za-g2.ctb~ 242, ~ru-litbrl-detailed.utb~
175, ~ru-litbrl.ctb~ 140, ~sk-g1.ctb~ and ~malayalam.cti~ 64 each,
~en-ueb-g2.ctb~ 32, ~fr-bfu-g2.ctb~ 30, ...).

Two things changed the decision. The ties turned out not to be the
whole story: the single-rule trie nodes and the missing chain-order
keys (character definitions last, ~always~ after other rules, backward
output length) cost far more than the ties, and fixing them means
modelling liblouis's order anyway. And the rule order the first version
called a defect is how tables are written in practice, such as the
~en-in-g1.ctb~ override above, which no single upstream fix would
change. Keeping the content-based keys first preserves the first
version's principle where the rules do say something; definition order
only settles what they leave open.
